# FloodWatch ML upgrade plan: research-grade to operational-grade

## Target architecture

FloodWatch should evolve from the current single-station, discharge-only LSTM into a regional, multi-source forecasting pipeline. Google Research's open-source OpenHydroNet is the most relevant reference implementation; reuse and benchmark it instead of claiming a home-grown model is equivalent.

## Model layers

1. **Data quality and station readiness** — preserve source URLs/checksums, deduplicate station timestamps, report missingness and gaps, reject invalid targets, and block training if continuous target windows are insufficient.
2. **Regional hydrology model** — train across multiple catchments rather than one station. Use historical discharge plus meteorological hindcasts and forecast sequences. Include rainfall, temperature, humidity/evaporation where available, and static basin descriptors (area, elevation, slope, soil, land cover).
3. **Forecast LSTM architecture** — benchmark the existing LSTM against OpenHydroNet's Mean-Embedding-Forecast-LSTM and Handoff-Forecast-LSTM designs. The latter separate historical context from future forecast forcing.
4. **Flood-event emphasis** — evaluate peak flows and known flood events separately from average conditions. Use event-weighted losses only after confirming labels and avoid arbitrary universal thresholds.
5. **Uncertainty and calibration** — add ensemble/quantile forecasts and reliability checks; never present one point estimate as certainty.
6. **Hydraulic impact layer** — discharge forecasts alone do not identify flooded areas or depth. A separate, validated inundation model plus elevation/river geometry is required before mapping affected places.
7. **Honest evaluation** — chronological holdout, event-based scores, lead-day metrics, station-wise metrics, persistence and seasonal baselines, and no train/test leakage. Keep metrics out of the UI until generated by a completed run.

## Current verified baseline

The CWC/NWDP archive download and normalization succeeded in run #3: 33 resources, zero download errors, 4,050,146 rows examined, 4,050,111 written, 35 negative values rejected, 540 stations. That run's LSTM never started because the workflow passed empty CLI inputs. A workflow fix was committed; run #4 is checking the corrected defaults. No model RMSE is verified yet.

## Important constraint

The current normalized archive is discharge-focused. It does not provide the meteorological forecast sequences and static catchment attributes needed for a Flood Hub-class system. Do not label FloodWatch equivalent to Google Flood Hub until those data inputs, the forecast model, an inundation layer, and rigorous local validation are implemented.
